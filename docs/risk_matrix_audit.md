# Аудит механизма рисков и матрицы (до правок)

Дата: 21.09.2026, ветка `feature/matrix-export-ui`, состояние кода на коммите `708fbad`. Здесь описано то, что есть в коде, а не то, как должно быть. Дефекты собраны в конце.

## 1. Где хранятся риски

Таблица `risks` (`backend/app/db/models.py`, класс `Risk`) плюс три служебные таблицы.

| Поле | Тип | Кто заполняет |
|---|---|---|
| `id`, `session_id` | uuid | приложение |
| `kind` | str(10): `legal` \| `learning` | приложение (`learning` — ошибка самопроверки студента) |
| `risk_type` | str(60), ключ закрытого словаря `RISK_TYPES` | модель выбирает из словаря; `user_defined` — пользователь |
| `scope_key`, `norm_family`, `dedup_key` | str | приложение: `dedup_key = risk_type \| slug(scope) \| identity_key акта` (это и есть fingerprint) |
| `title`, `scenario`, `conditions`, `consequences`, `recommendation` | text | модель (`RiskCandidate`); у своего риска — пользователь |
| `category` | str | приложение (из словаря типов) |
| `status` | str(20): `open` \| `in_progress` \| `resolved` \| `needs_clarification` \| `not_applicable` | приложение при создании; пользователь — через `PATCH /risks/{id}` |
| `base_p`, `s` | int 1–5 | модель (`proposed_p/proposed_s`) с ограничениями методики; пользователь — ручной оценкой |
| `bonus_p` | int 0/1 | приложение (однократный бонус за новый независимый факт) |
| `p`, `score`, `level` | int, int, str | приложение: `p = final_p(...)`, `score = p × s`, `level = level(score)`; **`level` хранится в строке** |
| `p_reason`, `s_reason` | text | модель; при ручной оценке — пользователь |
| `clarification` | text | модель/приложение (почему не оценён) |
| `resolution_reason`, `resolved_by`, `resolution_pending`, `closed_at` | — | приложение по действию пользователя или по его сообщению |
| `origin` | `agent` \| `user` | приложение |
| `manual_ps` | bool | приложение при ручной оценке (аналог `edited_by_user`) |
| `pending_suggestion` | json | приложение: расхождение агента с ручной оценкой |
| `methodology_version`, `version`, `created_at`, `updated_at` | — | приложение |

Связанные таблицы: `risk_evidence` (основания: `kind` = `obligation` / `consequence` / `fact` / `message`, `ref_id` — id цитаты, факта или сообщения), `risk_status_events` (история: создание, статус, оценка, предложение), `session_facts` (факты пользователя и вопросы для уточнения).

## 2. Как появляется риск

Отдельный вызов LLM после проверенного ответа: `run_analysis` в `backend/app/services/rag/pipeline.py`. Модель получает JSON-контекст: вопрос, проверенный текст ответа, `citations` (только фрагменты, реально выданные этому ответу), известные факты, существующие риски, профиль, словарь `risk_types` и шкалы роли `risk_scales`. Промпт — `backend/prompts/analysis/analyze.md` (версия 3), ответ валидируется по JSON Schema `AnalysisResult` (`backend/app/schemas/llm.py`, кандидат — `RiskCandidate`). Эвристик по ключевым словам нет.

Затем `engine.apply_analysis` (`backend/app/services/risks/engine.py`) в одной транзакции:
* вычёркивает id цитат, которых не было в ответе (запись в `trace.analysis_stripped_ids`);
* сортирует кандидатов (сначала снятия, потом по убыванию P × S) и создаёт не больше `max_new_risks_per_answer` новых рисков (по умолчанию 3), лишние пишет в лог;
* дедуплицирует по `dedup_key`: найденный риск обновляется, копия не создаётся;
* кандидат **без нормы-обязанности** из цитат ответа не становится риском, но превращается в **вопрос для уточнения** («Нет нормативного основания в базе знаний для риска «…»»), и этот вопрос **показывается пользователю** на вкладке «Уточнения».

## 3. Параметры оценки

Две оси, P (вероятность) и S (последствия), обе 1–5. Модель предлагает `proposed_p`, `proposed_s` и причины. Приложение применяет правила: S ≥ 3 только при цитате-санкции; P ≥ 4 только при подтверждённых фактах; P = 5 только при продолжающейся ситуации; бонус +1 однократный. Текстовые формулировки делений есть для каждой роли: `backend/app/services/risks/scales/{student,entrepreneur,expert}.yaml`, загрузчик — `scales.py`. Эти же формулировки кратко продублированы в правилах 4–5 промпта.

## 4. Как считается уровень

`score = p × s` (`scoring.score`), уровень — `scoring.level(score)`. Пороги (4, 9, 15) задаются в `Settings.risk_thresholds` (переменная окружения `DOORAIN_RISK_THRESHOLDS`). Отдельного файла `config/risk.yaml` нет. Хардкод есть в двух местах:
* **frontend** `lib/risk.ts` → `levelOf()` жёстко содержит 4/9/15 (используется в предпросмотре «Свой риск»);
* уровень **сохраняется** в `risks.level` в момент пересчёта, поэтому смена порогов не перекрашивает уже созданные риски.

Функции `level_from(p, s)` нет. В схеме модели поля уровня нет, так что назвать уровень модель не может.

## 5. Как формируется матрица

`GET /sessions/{id}/risks/matrix` → `engine.matrix()`: 25 ячеек, в каждой `p`, `s`, `level` (по произведению координат), `count` (активные риски `open`/`in_progress` с такими P и S) и `risks[{id,title}]`. Рендер — `frontend/src/features/workspace/RiskMatrix.tsx`: фон ячейки — тинт уровня (у пустых и заполненных одинаковый), в углу текстовое сокращение уровня («средн.»), в центре число и до четырёх точек.

**Строка «закрывает риск 4» выводится не в матрице**, а в режиме «План-схема» (`PlanPanel.tsx`): на кнопке-бейдже шага написано `` `закрывает риск ${risk.score}` ``. Это шаблонная подпись, в которую подставлен балл P × S. Для пользователя она выглядит как служебное число: «4» — не номер риска, а его балл.

## 6. Где задаётся цвет

* Токены: `frontend/src/styles/tokens.css` (`--risk-*`, `--risk-*-tint`, `--on-risk`, `--on-risk-mid`); тинты отличаются от значений в новом ТЗ.
* `lib/risk.ts` → `levelVar()` возвращает `var(--risk-…)`.
* Инлайновые `style={{ '--level': levelVar(...) }}` на кнопках и карточках: `RiskCard`, `PlanPanel`, `TimelineFlow`, `ReasoningDrawer`, `ChatPanel`, `GraphView`, `StyleguidePage`, `components/ui.tsx`.
* Инлайновый фон: `RiskMatrix` (тинт ячейки, цвет числа и точек), `HistoryPage` (полоса распределения), `TimelineFlow` (кружок номера).
* Узлы графа: `GraphNodes.tsx` → `paint()` задаёт `--fill/--edge/--tint` инлайн; мини-карта и SVG/PNG-экспорт — через `cssVar()`.
* CSS: `.card-risk::before`, `.badge-level`, `.inline-note::before`, `.tooltip-card::before` берут `var(--level)`.
* PDF: `backend/app/services/exports/pdf.py`, константы `LEVEL_COLOR/LEVEL_TINT/LEVEL_TEXT` (копия значений токенов в коде).
* Хекс-литералов цвета риска во frontend-компонентах нет (это проверяет `acceptance.test.ts`); в backend хексы есть только в `pdf.py`.

## 7. Связь риска с основанием

Хранится. `risk_evidence(kind='obligation', ref_id=citations.id)` → `citations.chunk_id` (фрагмент базы знаний) + `citations.snapshot` (реквизиты акта, редакция, локатор на момент ответа) + `excerpt`. Цитата принадлежит конкретному запуску ответа (`citations.run_id`), и это аналог `answer_traces`. Идентификаторы найденных фрагментов и их скоры дополнительно лежат в `generation_runs.trace`. Отдельного FK от `risk_evidence.ref_id` к `citations` нет (поле полиморфное). **Проверки типа источника нет:** учебник (`documents.doc_type = textbook`) или разъяснение (`soft_law`) может стать основанием риска. Это дефект.

## 8. Жизненный цикл

Статусы: `open` → `in_progress` → `resolved` (в ТЗ — `closed`); `not_applicable` («Неприменимо ко мне», в ТЗ — `dismissed`) с обязательной причиной; `needs_clarification` — кандидат с основанием, но без оценки. При закрытии пишется `closed_at`, событие истории, увеличивается `version`, растёт `session.version`. Граф пересчитывается на чтении (`portrait/graph.view`): цвет узла — максимальный уровень **активных** связанных рисков, у закрытых остаётся `resolved_level` («след»). Матрица и сводка считают только активные риски, поэтому закрытие убирает риск из ячейки. Если после снятия пришли новые независимые факты, риск снова открывается.
