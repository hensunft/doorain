# Методология рисков (версия 0.1-experimental)

> **Экспериментальная методика.** Она качественная: P и S — экспертные шкалы, а не вычисленная вероятность штрафа. До проверки практикующим юристом строки таблицы не являются юридической оценкой. Версия методологии записывается в каждый риск и в PDF.

## Шкалы (1–5), score = P × S

| P | Смысл при достаточных фактах |
|---|---|
| 1 | Условия риска маловероятны в описанном сценарии |
| 2 | Риск зависит от дополнительных факторов |
| 3 | Описанный сценарий типично создаёт риск |
| 4 | Пользователь **прямо сообщает** действия, поддерживающие вывод о риске |
| 5 | Пользователь сообщает о **продолжающейся** ситуации, удовлетворяющей проверенным условиям; это не судебное установление нарушения |

| S | Базовый смысл |
|---|---|
| 1 | Незначительные последствия, легко исправить |
| 2 | Умеренные: доработка, претензия и аналогичные подтверждённые последствия |
| 3 | Существенные последствия для деятельности |
| 4 | Серьёзные: значимые санкции, блокировки, иски — при наличии источников |
| 5 | Критические последствия либо иная подтверждённая особо тяжёлая ответственность |

Уровни по умолчанию: 1–4 низкий, 5–9 средний, 10–15 высокий, 16–25 критический (`test_level_boundaries`). Границы и лимит новых рисков — в `backend/app/config/risk.yaml` (`risk_thresholds`, `max_new_risks_per_answer`); переменные `DOORAIN_RISK_THRESHOLDS` / `DOORAIN_MAX_NEW_RISKS_PER_ANSWER` имеют приоритет. Уровень считает приложение (`scoring.level_from(p, s)`), модель уровень не называет — в её схеме такого поля нет. Сохранённые уровни — кэш: при старте API пересчитываются, поэтому смена порогов перекрашивает матрицу, список и граф без правки кода (`test_threshold_change_recolors_existing_risks`, границы 4/5, 9/10, 15/16 — `test_level_from_boundaries`).

Формулировки шкал для каждой роли — `backend/app/services/risks/scales/<role>.yaml` (`measure`, `probability` 1–5, `severity` 1–5). Модель получает шкалу своей роли в контексте анализа; полнота файлов проверяется тестом `test_role_scales_are_complete`.

## Правила создания и оценки (реализованы в `services/risks/engine.py`)

1. **Без проверенного нормативного основания риска нет.** Основание — только фрагменты, которые реально ушли в этот ответ (цитаты запуска), и только нормативный акт (`doc_type = npa`): учебник и разъяснение поясняют, но риск не создают. Кандидат без такого основания отбрасывается с записью в лог и пользователю не показывается (`test_risk_basis_must_come_from_the_actual_answer_context`, `test_textbook_is_not_a_risk_basis`).
2. **Норма об обязанности ≠ размер штрафа.** Основание последствий хранится отдельно. **S ≥ 3 допустима только при источнике последствий** (санкционная норма в корпусе); иначе кандидат остаётся `needs_clarification` вне ранжированной таблицы.
3. **P ≥ 4 требует подтверждённых фактов пользователя**; без них P ограничивается 3 с записью причины. Вопрос («Нужна ли политика?») фактом не является и не порождает утверждение «политики нет».
4. Нехватка фактов → `needs_clarification` без P/S (не выдумываем числа).
5. **Дедупликация** по `(risk_type из закрытого словаря, сценарий/объект, семейство нормы — документ без учёта редакции)`. Новая редакция не создаёт второй риск.
6. **Бонус P.** Только **новый независимый подтверждающий факт** по тому же сценарию (новый ключ факта) даёт **однократный бонус +1** к базовой оценке, максимум 5. Базовая оценка и бонус хранятся раздельно; факт не учитывается дважды (evidence с ролями `base`/`bonus`). Повтор, retry, перефразирование, повторная выдача SSE P не повышают. Итоговая P=5 допустима только при факте продолжающейся ситуации (иначе ограничивается 4): арифметика бонуса не доказывает «продолжается».
7. Уточнение/противоречие: новый факт с противоположным значением заменяет прежний (история сохраняется), база пересчитывается, бонус сбрасывается; оценка может снизиться.
8. **Снятие.** По однозначному сообщению пользователя: статус `resolved`, автор «по сообщению пользователя», причина и исходное сообщение; интерфейс показывает «Снят по сообщению пользователя (не независимая проверка устранения)». Неоднозначно — `resolution_pending` и подтверждение владельцем. Новые независимые факты снова открывают риск с записью причины.
9. Сортировка активных: score, затем S. Снятые и «требуют уточнения» — отдельные списки.
10. **Не более 3 новых рисков на ответ** (`max_new_risks_per_answer`). Дубли схлопываются по `dedup_key` (тип + предмет + акт) — это и есть fingerprint; у найденного риска растёт счётчик упоминаний (`mentions` = число сообщений, где он всплывал) и обновляется дата. Кандидаты сортируются по P × S; снятия и обновления существующих рисков под ограничение не попадают. Неизвестные модели `[C#]` вычищаются из кандидата (записываются в trace), а не валят анализ.
11. **Ручная оценка.** Пользователь может задать P и S с обязательной причиной — риск получает `manual_ps`. Агент такую оценку не перезаписывает: при расхождении он сохраняет `pending_suggestion` («есть уточнение»), пользователь принимает или отклоняет его.
12. **Свой риск** (`origin=user`, `risk_type=user_defined`) создаётся без нормативного основания, помечается «добавлен вами» и не участвует в оценке качества извлечения.
13. **Статусы.** `open` → `in_progress` → `resolved` (в API также `closed`); терминальный `not_applicable` («Неприменимо ко мне», в API также `dismissed`) требует причины. Ручная оценка хранится флагом `manual_ps` (аналог `edited_by_user`). У закрытых фиксируется `closed_at`; в списке они идут в конце, приглушённые; в графе остаётся след прежнего цвета.
14. **Выгрузки.** `GET /sessions/{id}/risks/export?format=csv` (разделитель `;`, BOM для Excel) и `format=md` (чек-лист «Сделать сейчас / В ближайший месяц / Мониторинг» + свои шаги + закрытые); PDF «Правовой слепок сессии» с матрицей и карточками рисков — кнопка «Выгрузить PDF».

## Ролевые рубрики

| Роль | Что такое риск | Что означает S |
|---|---|---|
| Студент | Только **подтверждённые ошибки понимания** из самопроверки; вопрос сам не доказывает незнание. Норма подтверждает *верное* понимание. | Важность понятия для темы (1–3), не санкция |
| Предприниматель | Правовые риски деятельности: штрафы, блокировки, претензии, утечки | Последствия для бизнеса при наличии источника |
| Эксперт | Риски применения: коллизии, спорные толкования, смена редакции | Последствия ошибочного применения нормы |

Учебные риски: `kind=learning`; P=2 при первой ошибке по понятию и 4 при повторной (независимые попытки); деловые риски у студента не создаются, самопроверка не создаёт деловых рисков.

## Требуется от юриста

Утвердить шкалы и словарь типов (`services/risks/methodology.py`), подобрать источники санкций, проверить бонус P и педагогическую рубрику; после этого изменить `METHODOLOGY_VERSION`.
