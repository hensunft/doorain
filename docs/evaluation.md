# Оценка качества и измерения

Раздел отделяет **проверку стенда** (работает ли конвейер, честны ли отказы, укладывается ли время) от **юридического качества** (правильны ли выводы). Первое измерено автоматически; второе без корпуса нормативных актов и юриста-эксперта измерить нельзя, и никаких оценок «точности» здесь нет.

## 4. Скорость (профиль `laptop-16gb-6gb`, RTX 4050 Laptop 6 ГБ, демо-корпус)

Первый полезный текст — первое событие `answer_delta` с текстом абзаца (статус/spinner не считается). «Весь цикл» — до `completed` (ответ + аналитика + граф + риски).

| Прогон | n | Первый текст p50 / p95 | Весь цикл p50 / p95 | Цель ТЗ |
|---|---|---|---|---|
| Soak: 10 вопросов подряд (`evals/live_check.py --brief`), все `validated`, unsupported = 0 | 10 | **5,64 с / 8,46 с** (min 4,61) | **19,4 с / 38,7 с** (min 13,8, max 38,7) | ≤5 с / ≤40 с |
| Holdout: только `validated` | 4 | 5,89 с / 8,45 с (cold 8,45 с) | 11,2 с / 18,1 с | |

Итог по целям: **≤5 с до первого текста не достигнута** (p50 выше на ≈0,6 с, p95 на ≈3,5 с); **≤40 с на цикл достигнута с малым запасом** (p95 38,7 с из 40). На 10–38 запросах p95 статистически непрочен.

Разложение (soak, тёплый стек): классификация ≈1,3–1,6 с; поиск при тёплых моделях — эмбеддинг ≈0,3 с и реранк ≈0,3 с; генерация ответа 0,9–4,2 с; оценка промпта 1,75–2,05 тыс. токенов из бюджета 4096. **Cold**: первая загрузка BGE-M3 ≈6,9–8,9 с и реранкера ≈2,3–2,8 с, первый вопрос после старта 11–13 с до текста — см. §7 про прогрев. Отказы (без генерации) укладываются в 1,6–3,1 с.

Ресурсы (50 замеров soak + прогон holdout):

| Ресурс | Пик |
|---|---|
| VRAM | 3135 МиБ из 6141 (модель + KV-кэш 4096) |
| Загрузка GPU | до 99 % |
| Температура GPU | 45 → 78 °C; частота SM 210–2460 МГц; мощность до 80 Вт (питание от сети) |
| RAM контейнеров | ollama 1,7–4,1 ГиБ, worker ≈1,2–1,35 ГиБ, api ≈0,1 ГиБ, postgres/qdrant/web < 0,1 ГиБ |
| RAM хоста | свободно упало до ≈0,5 из 15,7 ГБ (без OOM и swap-штормов за прогон) — запас на 16 ГБ **тонкий**; `.wslconfig` не менялся, предложение — в `docs/deployment.md` |

Троттлинг отдельно не анализировался (сэмплер пишет только min/max частоты и температуру); длительная (десятки минут) нагрузка не проверялась.

## 5. Выбор модели

Измерен **один** кандидат — `qwen3:4b-instruct-2507-q4_K_M`. Второй (`qwen3:4b-q4_K_M`, `think:false`) и модель меньшего размера **не сравнивались**: сравнение не завершено. Стенд для него есть (`evals/configs/laptop-16gb-6gb.json`, `run_eval.py` пишет digest/квантизацию/контекст в отчёт); сменить модель — `DOORAIN_OLLAMA_MODEL=<tag>` в `.env` и `prepare` при наличии интернета (`docs/deployment.md`), затем повторить прогоны на **том же** корпусе. Выбор по качеству и скорости вместе возможен только после появления реального корпуса и разметки.

Что показала 4B-модель на реальном стеке:
* Ответы по найденным нормам — обоснованные, с проверяемыми цитатами; непроверяемые блоки заменяются (`answer_block_replaced`) или отклоняются — `unsupported = 0` на soak.
* Извлечение **фактов пользователя** — надёжное; **кандидаты рисков** — ненадёжные: поля `proposed_p/proposed_s`, типы риска и ссылки на последствия часто пусты или неверны. По правилам методологии такие кандидаты не создают активный риск, а попадают в `needs_clarification` (безопасное поведение). Качество автоматического выделения рисков на 4B ограничено; повышение — крупнее модель (другой профиль) либо разметка/дообучение.

## 6. Калибровка порога

`DOORAIN_MIN_RERANK_SCORE` — порог на **необработанном** score реранкера, не вероятность. Процедура (`run_eval.py --split calibration`): среди значений лучшего rerank-score выбирается порог с максимальной сбалансированной точностью — доля отвечаемых кейсов с score ≥ порога и доля ловушек с score < порога, усреднённые (`calibrate()`); предложение (`calibration_suggestion`) пишется в отчёт. `--write-thresholds` (допустим только на `calibration`) сохраняет его в `evals/configs/thresholds.json` и печатает строку для `.env` (`DOORAIN_MIN_RERANK_SCORE`, `DOORAIN_THRESHOLD_SOURCE`) — приложение файл само не читает, порог принимает владелец. Калибровочный прогон **не выполнялся**: на демо-корпусе нет осмысленных пар «отвечаемый/ловушка с поиском», любое число было бы подгонкой. Порог остаётся `0.0`/`uncalibrated`, это видно в диагностике и в `model_info` каждого запуска. **Нельзя** подбирать порог на `holdout`.

Наблюдение на реальном реранкере: при несовпадении лексики вопроса и норм лучший score опускается ниже нуля (−1,35; в мультитурновом уточнении −0,13), поэтому порог `0.0` даёт честный `insufficient_grounds` вместо ответа «из памяти». Это правильное поведение при нехватке оснований, но порог нужно откалибровать на реальном корпусе, иначе ложные отказы неизбежны.

## 7. Что нашли реальные прогоны и что исправлено

| Находка | Исправление |
|---|---|
| Трасса (`run.trace`) не сохранялась при отказе: JSON-колонка не замечала мутацию на месте | Присваивается копия `dict(trace)`; тесты |
| Не сохранялась сырая выдача модели | Сохраняется в `trace.raw_answer` и `trace.analysis.raw` (аудит: `GET /runs/{id}/trace`, владелец) |
| Вводные абзацы без ссылки помечались `unsupported` | Промпт `rules.md` v2: вывод — в первый абзац со ссылкой |
| Неверный `risk_type`/темы на 4B | Словарь `risk_types` в контексте анализа (`analyze.md` v2); темы вопроса — от классификатора |
| Сбой в аналитике оставлял run «зависшим» | Перехват + пометка `analysis_failed` воркером; повтор анализа без второго сообщения |
| Индекс с другим эмбеддером | Явный отказ `index_incompatible` |

Не исправлено: TTFT p50 ≈5,6 с выше цели 5 с. Он складывается из классификации (≈1,5 с), поиска (≈0,6 с в тёплом состоянии) и генерации первого абзаца, который по ТЗ показывается только после структурной проверки ссылок. Возможные пути — прогрев моделей при старте (сейчас не реализован; первый запрос после старта 11–13 с), меньший `rerank_keep`, более короткий первый абзац — не реализованы, чтобы не менять поведение без измерений.

## 8. Как повторить

```powershell
$env:DOORAIN_EVAL_PASSWORD = '<пароль владельца>'
uv run --project backend python evals/run_eval.py --base http://127.0.0.1:8080 --user <логин> --split holdout --profile laptop-16gb-6gb --sample-resources
```

Для реальной оценки: (1) загрузить проверенный корпус и активировать generation; (2) прогнать `--split calibration`, принять порог осознанно; (3) прогнать `--split holdout` один раз; (4) отдать `*-expert.csv` юристу. Отчёт помечает прогон, если провайдеры тестовые или корпус содержит демо-данные (предупреждение в `caveats`). Быстрая проверка одного вопроса с таймингами — `evals/live_check.py` (внутри контейнера `api`).

## 9. Ограничения

* Нет реального корпуса и экспертной разметки → юридическое качество, содержательная корректность ссылок, согласие по рискам и полнота портрета **не проверены**.
* Ожидаемые темы/акты в наборе — гипотезы; набор мал (74), доверительные интервалы не считались.
* Измерено на RTX 4050 Laptop, не на целевой GTX 1660 Ti; Linux-путь и CPU-only профиль скорости не измерялись.
* Сравнение моделей не завершено (один кандидат); LLM-as-judge и RAGAS не применялись.
