# Доступ через интернет

Приложение публикуется **одним владельцем** по HTTPS с обязательным входом. AI-обработка и хранение выполняются на вашем сервере; доступ к результатам — по HTTPS (браузер владельца получает ответы, поэтому «данные вообще не покидают компьютер» утверждать нельзя). Публичного demo-режима без входа нет.

## Что нужно от владельца (это нельзя подготовить кодом)

1. Домен, принадлежащий вам, и DNS-запись `A` (и `AAAA`, если есть IPv6) на **публичный** IP.
2. Публичный IP или доступный IPv6 на подключении (не CGNAT — см. ниже).
3. Проброс портов **80 и 443** (TCP; 443/UDP для HTTP/3) с роутера на этот ПК и разрешение во входящем брандмауэре Windows/Linux. Скрипты правил брандмауэра и роутера **не меняют**; пример правила Windows (выполните сами):
   `New-NetFirewallRule -DisplayName "DoorAIn HTTPS" -Direction Inbound -Protocol TCP -LocalPort 80,443 -Action Allow`

## Запуск

В `.env` задайте `DOORAIN_DOMAIN=doorain.вашдомен.tld`, затем:

```powershell
scripts\doorain.ps1 doctor -Internet -Gpu     # домен не placeholder, только web публикуется, api/worker/БД без edge-сети
scripts\doorain.ps1 start -Internet -Gpu
```

Профиль `compose.internet.yaml` **отказывается стартовать**: без `DOORAIN_DOMAIN`, с placeholder-доменом (`example.*`, `your-domain*` — проверяет Caddy-entrypoint и приложение), со слабым `DOORAIN_SECRET_KEY`, без `Secure`-cookie. Публикуются только 80/443 (`ports: !override`); Ollama, Qdrant, PostgreSQL и API наружу не публикуются, Caddy admin API выключен.

Caddy сам получает и продлевает сертификат (нужна доступность 80/443 из интернета и постоянный том `caddy_data`). SSE проксируется без буферизации (`flush_interval -1`).

## Проверка с внешней сети (не из локальной сети!)

* С мобильного интернета откройте `https://ваш-домен` — должна открыться страница входа без предупреждений сертификата.
* `curl -sI https://ваш-домен | findstr /i "strict-transport content-security x-frame"` — заголовки безопасности.
* Cookie входа имеет префикс `__Host-`, `Secure`, `HttpOnly`; вход без пароля невозможен; `/api/docs` возвращает 404.
* `scripts\doorain.ps1 doctor -CheckPublic` (явный запрос к api.ipify.org): сравните публичный IP с WAN-адресом роутера.

**Статус в этой поставке:** конфигурация проверена локально (`docker compose config`, отказ без домена, эффективные порты). **Реальный внешний smoke-тест не выполнялся**: нет домена, публичного IP и доступа к роутеру.

## Если входящее соединение невозможно (CGNAT)

Признак: WAN-адрес роутера отличается от публичного IP (из `-CheckPublic`) или находится в диапазоне `100.64.0.0/10`. Port forwarding при этом **не поможет**. Варианты:

| Вариант | Суть | Границы доверия |
|---|---|---|
| Заказать у провайдера публичный (белый) IP | Обычная схема выше | Как у публичного сервиса |
| Приватный VPN (WireGuard и т. п.) | Доступ только вашим устройствам к серверу; нужен **достижимый peer/relay** (сам WireGuard CGNAT не устраняет) | Это не публичный сайт; посторонние не видят его |
| Отдельный явно выбранный tunnel/VPS | VPS с публичным IP пробрасывает трафик к вам | VPS/провайдер туннеля видит метаданные (и содержимое, если терминирует TLS). Выбирайте TCP-passthrough и понимайте риск |

Cloudflare Tunnel, ngrok и внешний TLS-terminating proxy **не подставляются по умолчанию** — это решение владельца.

## Эксплуатация публичного сервиса

* Сильный пароль владельца; при подозрении — `reset-password` (отзывает все сессии) и смена `DOORAIN_SECRET_KEY`.
* Динамический IP: DDNS — внешний сервис, подключается вами самостоятельно.
* Регулярные `backup` на отдельный носитель; обновления образов после `backup`.
* Если сервис доступен всем в интернете: отвечает владелец за соответствие 152-ФЗ и другим требованиям (дисклеймер в приложении не заменяет юридическую оценку).
